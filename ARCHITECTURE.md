# Cookbook architecture

This document separates shipped behavior from the approved target direction. Planned capabilities are not claims of shipped behavior. See the [roadmap](docs/roadmap.md) and [recipe publication guide](docs/recipe-publication.md).

## Current implementation

Cookbook is an independently served Go API with SQLite and local media. Astro builds the frontend as static output; Caddy serves it and proxies same-origin `/api/*` and `/healthz` to Go. There is no Astro server runtime. `/` remains the Home route for its remaining recipe interactions. `/discover` and `/create` are separate Astro static document routes with independent Discover and Create roots; each owns its session provider instead of importing the Home application. Discover is a read-only local catalog surface: signed-in viewers use actor-readable recipe and cookbook catalogs, anonymous viewers use public recipe and cookbook catalogs, and courses use the enabled public catalog. It does not query external discovery sources or indexes, or aggregate remote catalogs. Create requires a signed-in session and reuses the existing recipe, cookbook, and course forms. The extracted `CourseForm` feature is shared by the Home course-management surface and Create. Primary navigation includes Home, Discover, and Library, plus Create for signed-in users; Account and capability-gated Instance navigation remain available.

Library, recipe detail, cookbooks, cookbook detail, creator profile, account security, instance settings, the instance workbench, and `/auth/confirm` also use separate route roots and hydrate their page-specific UI. These roots can share session, navigation, and feature components without routing every page through Home. The confirmation route has a direct root; it uses the shared confirmation flow and continues to Home only after the user confirms. Static shells contain no account, authority, transfer, or cookbook data and use the authenticated or public APIs after session resolution. The separate `marketing-site/` is outside the application build. The new Astro routes are static output; their direct-route/CSP behavior still requires verification on the canonical Caddy serving path. Static standalone delivery remains the default; a request-time public renderer is not part of the shipped deployment.

SQLite uses WAL, foreign keys, one application connection, and an ordered, checksummed migration ledger that currently reaches v14. Migration v7 introduced creator profiles with typed recipe/cookbook attribution, v8 added saved-cookbook references, and v14 extends creator claims to courses. Migration definitions are immutable after application; new schema belongs in later ordered migrations.

Local accounts authenticate through email links when email delivery is configured and through passkeys. Operators can use a read-only exact-email account lookup when the server is stopped, and can issue or revoke a one-time, short-lived initial passkey enrollment grant for an existing account without an email link. Instance-owner claim, transfer, and recovery are explicit account-ID operations. These controls do not infer ownership or role from email. Instance ownership, administrator authority, recipe ownership, and creator attribution remain distinct.

Migration v7 adds account-owned creator profiles with `private|instance` visibility and typed recipe/cookbook attribution. Migration v14 adds course creator claims and an unverified course name claim without changing earlier migration definitions. Authenticated profile reads never grant access to an attributed resource; profile catalog queries apply both profile visibility and the existing resource ACL. Recipe and course self-attribution are create-only, cookbook creation and fork adaptation are transactional, and legacy bylines remain unverified text. Course API creation accepts optional attribution for old-client compatibility; `/api/public/config.course_creator_attribution` signals API support separately from `courses_enabled`. Course detail, list, public list, and available Library projections batch claims with the resource ACL in a consistent SQLite query snapshot; anonymous public courses may show external claims and name claims but not local profile identity. Course attribution controls in the frontend and archive v9 support remain unimplemented; archive export/import stays v8 and does not carry course creator claims. Portable recipe export preserves external attribution claims without binding them to the importer. Instance-visible profiles and attribution views are available inside Cookbook; they do not verify external identity or provide public actor publication. See [Local creator profiles](docs/creator-profiles.md).

Migration v8 adds account-owned saved-cookbook references. A reference stores the source instance namespace, cookbook ID, and save time; it is not membership, a snapshot, a copy, or an access grant. Current cookbook access is checked when a reference is read, and unavailable entries are redacted. Authenticated `GET /api/library/cookbooks?limit=24&offset=0` returns a paged, deduplicated union of owned, current-member, and exact same-instance saved cookbooks in one read-only query. Authenticated `GET /api/library/recipes?limit=24&offset=0` returns a paged union of owned, currently shared, recipes in an owned cookbook when canonical recipe ACL independently permits access, local saved recipes, validated cached remote snapshots, and redacted unavailable saved references. Stable canonical recipe identity is merged before paging; separate adaptations remain separate resources. Exact local saved state comes from the account's saved-reference relation. Remote recipe detail is authenticated and cache-only: it accepts an exact remote object URI whether or not it is bookmarked, verifies the cached object/source/recipe binding, and returns `404` for unavailable or stale source binding; it does not fetch the source or grant access. Saved-reference APIs and portable export/import v5 are implemented, with v1–v4 imports preserved. The Library route consumes the typed recipe and cookbook queries and saved-state operations; saved references expose no additional resource access.

Person-actor identity persistence is present: an existing account can have one optional actor with a pinned canonical origin, opaque stable ID, and Ed25519 key material. A read-only recovery `describe`/`verify` command validates the active actor-key binding and compares the database actor set with a manifest; retired actors are represented without a key fingerprint. A disposable schema-v8 cold/WAL restore fixture passed with local and foreign saved-cookbook references, actor/key manifest checks, creator-profile and attribution data, and a WAL-resident marker; it also verifies the v8 ledger, SQLite integrity and foreign keys, and negative constraint cases. This is synthetic fixture evidence, not an end-user backup workflow, real archive rehearsal, or production recovery guarantee. Public actor documents, actor routes, and ActivityPub publishing remain unimplemented.

Personal portability archives use format v8 for owner-authorized private remote snapshot preservation. Snapshot bodies and captured evidence are stored in separate bounded ZIP entries referenced by the manifest; the opaque claim preserves raw source facts and is not a trust credential. Export requires an active, unrestricted owner snapshot. Import defaults to reference-only; authenticated request header `X-Cookbook-Preserve-Personal-Snapshots: true` explicitly requests same-person preservation through the Core importer, which forces `user_imported_unverified` and does not promote trust. Existing destination pins conflict. This archive path does not fetch a source, redistribute content, or enable live profile activation. Imports of v1–v7 remain supported.

Recipe reads use a typed query boundary. The API applies owner, cookbook-membership, instance, visibility, deletion, and publication policy before returning recipe data. Authenticated recipe read projections include `owner_id` only for the recipe owner; authorized non-owners retain their `can_edit`, `can_delete`, `can_manage_sharing`, cookbook, and source-link projections without receiving the owner account ID. These response fields do not change persisted ownership or authorize requests. Cookbook ownership alone does not grant access to another account’s private recipe; editor rights remain subject to the recipe’s edit policy. Admin status does not bypass content privacy. Attribution and source references are claims, not verified identity.

### Independent content controls

The API keeps these controls separate:

- **Visibility** controls the local audience (`private`, `unlisted`, or `public`). Unlisted recipes are not capability URLs. Anonymous reading requires a public instance, public visibility, an active recipe, and published lifecycle state.
- **Publication lifecycle** controls inclusion in anonymous local recipe lists and other public projections (`unpublished`, `published`, or `withdrawn`). It never changes visibility.
- **Federation consent** controls outbound Exchange v1 recipe delivery (`off` or `followers`). It defaults off and is independent of local public browsing. “Followers” is the policy value; current v1 delivery still uses administrator-enrolled peers, not open ActivityPub follows.
- **Index eligibility** is represented in the policy, but index submission/removal is not implemented. The API rejects `index_eligible: true`.
- **Discovery consumption** is a separate future choice about which sources a user or instance queries. The current Discover page reads actor-readable local recipe and cookbook catalogs for signed-in viewers, public local recipe and cookbook catalogs for anonymous viewers, and the enabled public course catalog. External source adapters, index queries/submission, normal public follows, and cross-source result aggregation remain unimplemented. A search result must not grant access to its source.

### HTTP, privacy, and publication routes

- `/api/auth/*` provides email-link authentication, sessions and passkey ceremonies. Tokens are hashed; sensitive changes have recent-authentication requirements where specified.
- `POST /api/recipes` creates an owned recipe. New records default to private visibility and unpublished/off/no-index policy. Public visibility requires `confirm_public_access: true`; an optional `initial_publication` chooses initial local lifecycle and federation consent in the same transaction.
- `/api/recipes` and `/api/recipes/{id}` provide authenticated recipe lists, detail, edits, and soft deletion. Related routes handle revisions, trash/restore, forks, owner transfer, publication policy, and visibility-checked images. Recipe owners alone can manage publication policy and transfer ownership.
- `GET` and `PUT /api/recipes/{id}/publication` are owner-only. The response is private/no-store and includes a strong ETag; PUT requires the exact current ETag in `If-Match`. This endpoint does not edit recipe body or local visibility. Details and error handling are in [Recipe publication](docs/recipe-publication.md).
- `GET /api/public/recipes`, `GET /api/public/recipes/{id}`, `/api/public/cookbooks*`, and public course routes expose policy-filtered public projections. Authenticated `/api/recipes/{id}` remains behind session middleware. Public API detail does not create request-rendered pages; a request-time public renderer remains optional future work.
- `/api/cookbooks*`, `/api/library/bookmarks`, `/api/library/cookbook-bookmarks`, and authenticated `GET /api/library/recipes` and `GET /api/library/cookbooks` provide typed personal-library reads and local saved-reference operations. Each returns its resource type's owned, related, and eligible saved entries after current access checks; neither aggregates remote sources. `/api/admin/*`, `/api/instance/*`, `/api/export`, and `/api/import` provide administration, explicit owner operations, and portability. General instance settings use a separate server capability granted to the current instance owner or an administrator. Owner status does not set the administrator role or grant content access; transfer, role, federation-management, and content actions retain their own policy checks.

API JSON and token-bearing authentication responses are `no-store`. Browser mutations retain same-origin/CSRF checks, secure host-only cookies, bounded input, and required recent-auth checks. The federation inbox uses its signed server-to-server profile. Static-page CSP hashes come from the frontend build; Go owns API security headers. API/health paths must not fall through to static HTML.

### Federation and delivery

Exchange v1 remains an opt-in, administrator-enrolled peer protocol for allowlisted public recipe snapshots, updates, and tombstones. The strict wire DTO and JSON syntax codec is isolated in `internal/federation/exchangev1`, with a standard-library-only production import allowlist exercised by its package tests. The main adapter retains canonical recipe normalization, event and origin/object validation, publication eligibility, and compatibility mapping. Delivery uses signatures, replay/order checks, and a transactional retrying outbox. The v1 sender requires current public-instance, public-visibility, active, published, and explicit owner `followers` consent before emitting recipe-bearing events. Owner policy changes and required tombstones share a transaction; stale content is suppressed at delivery/retry boundaries. Consent defaults off, including for legacy recipes. V1 is a compatibility profile, not ActivityPub or private sharing. See [FEDERATION_PROTOCOL.md](FEDERATION_PROTOCOL.md) and [FEDERATION_RESEARCH.md](FEDERATION_RESEARCH.md) for wire behavior and threat limits.

## Approved target direction — staged, not shipped

Keep a modular Go application with explicit HTTP adapters, typed use cases/queries, authoritative local policy, and persistence-owned SQL. Extract seams incrementally; do not introduce microservices or a second application database without evidence. Recipe changes, revisions, and required outbox events remain transactionally consistent.

Keep local account IDs as authorization principals. Credentials, instance-owner authority, optional public actors, recipe owners, and attribution are separate. The actor tables and read-only key/database recovery validation are implemented; public actor resolution/signing endpoints, ActivityPub inbox/outbox/follow interactions, interoperability, abuse controls, and delivery safeguards remain future work. Exchange v1 is the only shipped federation profile; it does not publish Person actors.

Local recipe and cookbook saved references are implemented as identity references that resolve current access; cookbook-reference UI remains pending. Continue typed copies, adaptations, and provenance without changing legacy claims into verified identity. Collections reference content rather than duplicate it. Courses retain their educational meaning; meal menus are a separate future type. Account ownership and cookbook membership remain the current custody model unless a concrete group-custody need is approved.

Local FTS5 capability has been proven, but the user-facing local search implementation remains future work. Apply ACLs before returning hits, snippets, facets, counts, or images. External sources receive no private fields or account identity; query terms are visible/configurable. A result never grants access, and opening it rechecks the source.

Standalone remains one Go service, SQLite, local media, and an independently served static frontend. A future on-demand renderer is an optional profile only: it may serve explicitly public projections through Go’s policy boundary, preserve same-origin API routing, and never cache private or personalized HTML. It must not become mandatory for standalone use. Production deployment or account/infrastructure changes require separate authorization.

Architecture decisions record the problem, evidence, alternatives, compatibility impact, tests, and migration sequence in the project decision register. Primary specs and delivery gates are linked from the [roadmap](docs/roadmap.md).
